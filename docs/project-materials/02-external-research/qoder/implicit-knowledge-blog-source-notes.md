## 页面定位

这篇博客不是操作手册，而是 Repo Wiki 的产品解释：代码中分散、依赖经验才能理解的架构、引用关系和实现知识，可以被自动整理成团队共享的显性工程资产。

## 核心价值叙事

博客把价值分成两类：

1. **Agent 协作效率。** 结构化工程知识让 Agent 获得更完整的上下文，从而改善解释和开发回答。
2. **陌生项目理解。** 架构、模块关系和技术文档缩短新开发者理解代码库的时间，降低协作与维护成本。

它强调的不是文档数量，而是把原本依赖资深工程师经验和逐层追代码才能获得的信息，转成可共享、可复用的知识资产。

## 生成叙事

博客公开到的处理过程为：

```text
Repository
  -> 建立代码索引
  -> 多 Agent 分阶段分析与建模
  -> 规划文档结构
  -> 平衡知识深度与阅读效率
  -> 生成结构化 Wiki
```

其中“多 Agent”是该页比用户指南多提供的信息，但没有给出 Agent 角色、消息合同、Evidence Pack、验证过程、失败恢复或是否使用同一模型。

## 维护与共享

- 本地生成后创建 `.qoder/repowiki`。
- 目录可推送到远端分支，成为团队共同维护的知识资产。
- 自动检测代码变化并提醒更新 Wiki。
- 用户可以直接修改目录内容，再同步回产品。
- 页面还提到导出能力，但没有描述导出格式或数据合同。

## 最佳实践

### 智能对话

Agent 在回答仓库问题时使用 Wiki，提供代码解释、技术文档和实现细节。在新增功能或缺陷修复中，Agent 参考顶层架构并结合实时工程感知，目标是让新代码与现有架构保持一致。

### 代码库阅读

开发者通过架构说明、模块依赖图和技术实现文档建立整体认知，再进入局部源码。这是一种“先地图、后街景”的阅读路径。

## 与当前用户指南的差异

| 博客强调 | 当前用户指南补充 |
|---|---|
| 隐性知识显性化和团队资产 | `/knowledge` 的四种人工操作 |
| 多 Agent 分阶段建模 | `wiki_plan.yaml` 的具体字段 |
| 自动检测变化并提醒更新 | 只更新受影响部分、Git 同步路径 |
| 共享与导出 | Teams 自动共享、Git 共享、多语言和 Credits |

博客适合理解产品意图，用户指南更适合提取可验证的行为合同。二者合用，不能用博客中的市场叙事替代实际接口验证。
